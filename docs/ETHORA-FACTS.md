# Ethora facts verified on 17 Oct 2026

From the Ethora source as cloned that day (backend 2026-09-17, chat component clone 26.3.22 with npm latest 26.10.4) and the hosted MCP tool list. Re-verify against the public docs (`search` tool on the MCP, or https://ethora.com) before relying on exact shapes; the API may have moved on.

## Chat component (`@ethora/chat-component`, React)
Config (`IConfig`): `appId`, `baseUrl`, `customAppToken`, `xmppSettings`, `disableHeader`, `disableRooms`, `forceSetRoom`, `setRoomJidInPath`, `defaultRooms[]`, `customRooms { rooms, disableGetRooms, singleRoom }`, `backgroundChat { color, image }`, `colors { primary, secondary }`, `customLogin { enabled, loginFunction: () => Promise<User|null> }`, `userLogin`, `jwtLogin` (legacy), `refreshTokens`, `eventHandlers { onMessageSent, onMessageFailed, onMessageEdited, onMessageHistory?, onMessageError? }`, `messageTextFilter { enabled, filterFunction }`, `secondarySendButton`, `whitelistSystemMessage: string[]`, `customSystemMessage: ComponentType<MessageProps>`, `customTypingIndicator`, `disableChatInfo {...}`, `chatHeaderSettings { hide, disableCreate, disableMenu, hideSearch }`, `disableNewChatButton`, `disableUserCount`, `translates`, `inAppNotifications`, `pushNotifications`, `historyQoS`, `newArch`, `useStoreConsoleEnabled`.
Not found: an incoming-message event handler. Check the exported store/hooks (`roomStore`, `context`) at the installed version.

Corrections from the installed 26.10.4 (17 Oct, evening): `customRooms`, `singleRoom` and `forceSetRoom` do not exist in `IConfig` any more. Pin a room with the `roomJID` prop on `<Chat>` (full JID `${appId}_${chatId}@conference.<xmpp domain>`) plus `disableRooms`. Login as an injected user: `jwtLogin: { enabled, token }` where the token is the client JWT from `@ethora/sdk-backend` (`createChatUserJwtToken(userId)`, exchanged by the component through `loginViaJwt`), or `userLogin: { enabled, user }` with a full user object. Pass the same memoised config to `XmppProvider` and `Chat`. Two things learned the hard way (17 Oct, late): (1) `xmppSettings { devServer: 'wss://<xmpp domain>/ws', host, conference }` is required unless the host app sets `VITE_XMPP_HOST`; without it there is no WebSocket endpoint and the panel sits on "Connecting..." forever. (2) With `initBeforeLoad: true` the provider bootstrap stayed in `running` and the chat waited on it; `initBeforeLoad: false` (the Chat component initialises XMPP) works. The JWT exchange is `POST /v1/users/client` with header `x-custom-token: <client JWT>` and returns `{ token, refreshToken, user }` including `xmppUsername` and `xmppPassword`. Message bodies are rendered as markdown (a leading `* ` becomes a bullet). `useStoreConsoleEnabled: true` prints the internal `[InitPolicy]` / `[initBeforeLoad]` logs. Incoming messages: the `CustomScrollableArea` prop receives `messages: IMessage[]` and a `renderMessage` function, which is the supported way to observe the room's messages (bubbles). `useXmppClient()` exposes the raw xmpp.js client as a last resort. `CustomMessageComponent` gets `MessageProps { message, isUser, isReply }` for custom rendering of narration lines.

## Backend SDK (`@ethora/sdk-backend` 26.8.1)
Server side only. Env `ETHORA_CHAT_API_URL`, `ETHORA_CHAT_APP_ID`, `ETHORA_CHAT_APP_SECRET` (App Secret from the dashboard API tab; not obtainable over MCP). Signs a B2B server token (`x-custom-token`) per request. Methods used here: `createUser(userId, {firstName, lastName, email})` (batch endpoint; lastName must be 2+ chars), `grantUserAccessToChatRoom(chatId, userId)` / `removeUserAccessFromChatRoom` (`POST`/`DELETE /v2/chats/users-access` with `chatName = ${appId}_${chatId}`, members `${appId}_${userId}`), `broadcastToAppChats(appId, {text, chatNames, senderName, metadata})`, `createChatUserJwtToken(userId)`. Rooms created over MCP are public app chats: every app user is a member of all of them and `users-access` answers `CHAT_NOT_FOUND` for them (ETHORA-GAPS #10). `broadcastToAppChats` rejects a per-message `senderName` (422); the sender shown is the app's broadcast sender, which defaults to the app name. The broadcast posts from the app's system account (`senderKind: app`).

## Backend REST (base `/v1`, routes in `routes/chat.js`)
- Rooms: `POST /v2/apps/:appId/chats`, `GET /v2/apps/:appId/chats`, `PATCH /v2/apps/:appId/chats/:chatId`, `DELETE /v2/apps/:appId/chats`.
- Membership: `POST /v2/apps/:appId/chats/users-access`, `DELETE /v2/apps/:appId/chats/users-access`, `PATCH /v2/apps/:appId/chats/users`, `GET /v2/chats/users`, `GET /v2/apps/:appId/users/:userId/chats`. Remove-user sets the XMPP room affiliation (`set_room_affiliation`) and updates `user2chats`.
- Messages: `GET /v2/apps/:appId/chats/:chatId/messages`, `.../messages/context`, `DELETE .../messages`; broadcast `POST /v2/apps/:appId/chats/broadcast` + job polling.
- Agents: `POST /v2/apps/:appId/agents/:idOrAddress/invite-to-chat`, `POST /v2/agents/:idOrAddress/bot-instances/:botInstanceId/leave-chat`.
- Calls: `chat.call.ts` (WebRTC room calls; enabled on Ethora Cloud prod Oct 2026).
- Room JID: `${appId}_${chatId}@<xmpp domain>`; user JID `${appId}_${userId}@...`.

## Hosted MCP (`https://mcp.chat.ethora.com/mcp`, OAuth; also `/mcp/k/<key>`)
Doc upload works in user auth mode on the hosted server (used for the Hatter). `ethora-message-send` with `waitForReplySec` returns the agent reply; useful as a smoke test. Not present on the hosted tool list: `ethora-app-credentials-reveal` (so the App Secret comes from the dashboard).

## Legacy, do not use
`models/room.js` with `ownerNavLinks`/`userNavLinks` (N/E/S/W), `/v1/rooms`, `RoomFactory` contract, `scripts/linkRooms.js` ("Agora (Start here)"). Web3-era prototype of the same idea; unused by current clients.

- Calls (26.10.4, seen in the bundle 25 Oct 2026): the chat component has voice and video calls built on LiveKit. Signalling goes over XMPP as messages whose body is `call-invite`, `call-token`, `call-state`, `call-ringing`, `call-ended`, `call-declined`, `call-cancelled`, `call-timeout`, `call-rejected` (the component filters them out of the message list, ids `calllog-*` for the log entries); the client receives a `livekitToken` (also `callToken`) and `livekitUrl` with a `callKind` of audio or video and mounts `VideoCallOverlay`. No call config keys in `IConfig`; the MCP docs say calls and media live in the clients only (gap 24).
